## Findings

**1. BLOCKER — Capture time is not logged, so the offset (time) axis is silently corruptible and unverifiable.**
Evidence: `fable-lab/strategies/_fixtures/diag-calib.ts:71-77` — the loop captures *every* uncaptured offset ≤ elapsed on the first clean tick, and the log line carries only the *nominal* offset, not the capture timestamp. If a recording starts late or has a WS gap (E6's documented failure mode), a single tick at e.g. 860s stamps all 7 offsets with the same late-window ask, injecting expiry-regime prices (exactly the certainty-discount region EXP-001/E14 measured) into "30s"/"150s" cells as 7 duplicated observations. At ~50 events/sec this is rare in healthy recordings, but its frequency is unknown and — because `ts` is not logged — *cannot be measured post-hoc* from the log. A tail-offset candidate leaking into an early-offset cell is precisely the false positive this design exists to prevent.
Remedy: add `ts=<elapsedSec>` to the log line, freeze a drift filter in CALIBRATION.md now (e.g. discard samples captured more than the gap-to-next-offset after nominal), kill pid 44945 and relaunch — the run is minutes old and nothing has been read.

**2. MAJOR — The E14 positive-control gate has no frozen threshold and no abort; "instrument bug first" is post-hoc discretion.**
Evidence: `fable-lab/tools/calib.ts:136-141` prints the (850s, [0.90,0.98)) control but enforces nothing; `knowledge/CALIBRATION.md:98-100` says "a large deviation there means instrument bug first" without defining "large". The analyst decides *after seeing the number* whether to distrust the instrument — the exact escape hatch the one-shot design otherwise closes (an inconvenient table can be voided as "instrument suspect"; a convenient one accepted).
Remedy: freeze a numeric gate pre-results (e.g. abort iff |z_control| ≥ 3.377, mirroring the candidate bar) in both doc and tool.

**3. MAJOR — "A null closes the taker question plane-wide" overstates: the study measures only the buy-UP half of the taker plane.**
Evidence: `knowledge/CALIBRATION.md:89-91` and `DECISIONS.md:572-573` ("a null closes the taker question plane-wide within stated power"); `STATE.md:378` ("closing the taker plane"). The instrument samples the UP book's ask only. Buy-DOWN edge is (1−w) − askDOWN, and CALIBRATION.md:85-88 itself concedes the DOWN book has its own spread (askDOWN ≠ 1 − askUP). A null here says nothing about DOWN-side taker cells; NEG-FLAG only *motivates* that measurement. The power section is honest about mid-range; this specific "plane-wide" phrase is the one wording a successor could over-read into a LESSONS entry.
Remedy: amend all three files pre-results to "closes the buy-UP taker half-plane within stated power; DOWN-ask half-plane unmeasured".

**4. MINOR — Fee formula ignores that the engine takes BUY fees in shares, underestimating effective fee by factor w/a.**
Evidence: `src/trading/fees.ts:47` (`feeBase = rate·min(p,1−p)·(size/p)`, deducted from received shares, Portfolio.ts:680) means expected fee cost per intended share = w·0.0156·min(a,1−a)/a, vs the tool's `0.0156·min(meanAsk,1−meanAsk)` (calib.ts:117). On the diagonal w≈a it cancels; in a *candidate* low-ask cell (say meanAsk 0.05, winRate 0.12) actual fee is ~2.4× modeled (0.19c vs 0.08c) — still small against the ~multi-cent d required there, so it can only flip razor-thin `net>0` cases. (Opposing Jensen effect — fee at meanAsk over concave min() — is conservative.)
Remedy: note in CALIBRATION.md; optionally use `fee = winRate·0.0156·min(meanAsk,1−meanAsk)/meanAsk` — freeze the choice pre-results.

**5. MINOR — One-shot read is procedural, not mechanical.**
Evidence: calib.ts is freely re-runnable, buckets/thresholds are plain constants (calib.ts:21-35), and result_id is queryable in MySQL at any time; enforcement is the frozen committed doc plus git history ("changing a bucket … is a protocol breach", calib.ts:12-13). Consistent with the lab's acknowledged honor-system precedent (E19 erratum), but it should be named as such rather than implied to be mechanical ("mechanically honest", DECISIONS.md:580).
Remedy: one-line disclosure in CALIBRATION.md that the one-shot is honor-system + git-audit, as in E19.

**6. MINOR — Per-cell z assumes cross-market independence; serial regime correlation would inflate z.**
Evidence: se derivation (calib.ts:108,119) is exact only for independent markets; EPISTEMOLOGY §1 acknowledges adjacent 15m windows share regime. Deviations (wᵢ−aᵢ) of consecutive windows are plausibly weakly positively correlated (trend days cluster UP wins the ask hasn't fully priced), making true se somewhat larger than H0 se. The 3.377 bar leaves headroom, but a candidate with z barely over the bar built on temporally clustered wins is suspect.
Remedy: pre-commit a robustness check for any candidate (e.g. split-by-month sign consistency, or a block/cluster se by day) before it may be cited under §4 — freeze it now.

**7. MINOR — NEG-FLAG has no minority≥30 guard, re-opening the exact E14 blind spot on the negative side.**
Evidence: calib.ts:162-164 flags on `z ≤ −3.377` alone; in [0.98,0.995] cells the z is built on a handful of losses (E14's 7-losses failure mode). Low cost since a NEG-FLAG only motivates a pre-registered DOWN measurement, but a flag from <30 minority events is the same statistical artifact class D13 exists to prevent.
Remedy: report but annotate NEG-FLAGs with minority<30 as "underpowered, E14-class".

**8. MINOR — Offset coverage per column is a measurable selection effect the tool doesn't report.**
Evidence: a market missing a clean tick from offset t to 900s drops out of column t (diag-calib.ts:64-69); gap-heavy or pinned-quiet markets may drop out non-randomly, and the tool never prints markets-per-offset vs total (calib.ts prints only aggregate parse counts, :78). Unlike finding 1 this *is* computable post-hoc from the existing log (distinct slugs per off).
Remedy: add per-offset coverage counts (n markets / 8,516) to the printout as a diagnostic; disclose in interpretation.

**9. MINOR — Two cosmetic/comment inaccuracies.**
(a) calib.ts:80 comment "resolvedOnly default keeps unresolved out" is false — `getMarketsBySlugs` sets `resolvedOnly: false` (src/db/telonexMarkets.ts:349); behavior is still correct because only resultId '0'/'1' are accepted (calib.ts:88-89), but the comment misdescribes the safety mechanism. (b) calib.ts:153 prints the last bucket's label with `)` although it is inclusive (`[0.98,0.995]` per the frozen doc).
Remedy: fix comment and label; no behavioral change.
