# Protocol audit 2026-07-08--02

## Verdict

Audit 01's findings are resolved (A1–A4 fixed, A5 consciously skipped with
the threat model corrected by the new "The two bars" section). The protocol
is runnable and internally consistent on the big things. What remains is
second-order: the session STOP conditions are already enumerated in three
places and have already drifted apart (the new 200-experiment brake exists
in only one of them), and `propose-family.sh` ships a permission default
that its own module contract cannot run under. Nothing here blocks starting
research today.

## Findings

### B1 — Stop conditions enumerated in three places, already diverged

- **Status:** ✅ FIXED — researcher.sh instruction and SESSIONS.md now defer to the module's Session contract (the single home for stop conditions).

- **Severity:** medium
- **Category:** duplication / flaw
- **Where:** `strategy-research-protocol/modules/Researcher.md` (Session
  contract — the authoritative list, incl. the 200-experiment brake);
  `strategy-research-protocol/scripts/researcher.sh` (INSTRUCTION: "stop
  only when the family is validated, killed, or nothing is actionable" — no
  brake); `strategy-research-protocol/SESSIONS.md` (Launch modes bullet —
  same enumeration, no brake). The dashboard-down stop
  (`tools/getBacktestResults.md`) is a fourth stop condition absent from
  all three enumerations.
- **Problem:** The word "only" makes each enumeration a claim of
  completeness, and they already disagree: a session following the script
  instruction literally would ignore the brake the module added. Every
  future stop condition will have to be edited in three places or the drift
  compounds — exactly the failure One Home Per Concept exists to prevent.
- **Fix:** Make the module the single home. In `researcher.sh` shorten the
  instruction tail to "…stop per the module's Session contract"; in
  SESSIONS.md replace the enumeration with "stops when the Session contract
  says so (validated, killed, nothing actionable, or its runaway brake)" —
  loose summary, no "only".

### B2 — propose-family.sh defaults to a permission mode its module cannot run under

- **Status:** ✅ FIXED — propose-family.sh defaults to bypassPermissions, matching researcher.sh and the SESSIONS.md launcher checklist.

- **Severity:** medium
- **Category:** flaw
- **Where:** `strategy-research-protocol/scripts/propose-family.sh`
  (`PERM="${PERM:-acceptEdits}"`) vs
  `strategy-research-protocol/modules/ProposeFamily.md` (step 10 "Typecheck
  enough to catch API errors", Final Self-Check "`npm run research:check`
  passes") vs `strategy-research-protocol/SESSIONS.md` ("Writing a new
  launch script" item 5: default to `bypassPermissions` for headless,
  because headless DENIES non-allowlisted commands instead of asking).
- **Problem:** The proposer must run Bash (typecheck, `research:check`),
  but headless `acceptEdits` silently DENIES those commands unless
  allowlisted — the session ends with an unvalidated family and no visible
  error about why. The script also violates the checklist SESSIONS.md sets
  for every launcher.
- **Fix:** One line: `PERM="${PERM:-bypassPermissions}"` in
  propose-family.sh (and update its header comment), matching researcher.sh
  and the SESSIONS.md checklist.

### B3 — Stale multi-role phrasing survives in MEMORY.md

- **Status:** ✅ FIXED — MEMORY.md bullet rewritten: created by ProposeFamily, thereafter written by the Researcher.

- **Severity:** low
- **Category:** confusing
- **Where:** `strategy-research-protocol/MEMORY.md` ("The model"):
  "written by agents flipping the state they own and by the Researcher
  recording judgment".
- **Problem:** "Agents flipping the state they own" is Evaluator-era
  language — it implies multiple writers with partitioned ownership. Today
  FAMILY.json has exactly two writers: ProposeFamily (creation) and the
  Researcher (everything else). A reader can waste time hunting for the
  ownership partition that no longer exists.
- **Fix:** Rewrite the bullet: "**FAMILY.json = exact facts** (state +
  numbers), created by ProposeFamily and thereafter written by the
  Researcher."

### B4 — ENGINE.md "Research Scope" restates SCOPE.md

- **Status:** ✅ FIXED — ENGINE.md Research Scope shrunk to a pointer at SCOPE.md plus engine-only facts.

- **Severity:** low
- **Category:** duplication
- **Where:** `strategy-research-protocol/ENGINE.md` ("Research Scope"
  section: venue/instrument/symbol/timeframe/input/converter block, 96
  episodes/day) vs `strategy-research-protocol/SCOPE.md` ("Market scope",
  "Data source" — the home per the AGENTS.md ownership table).
- **Problem:** The scope facts are defined twice. If the user ever widens
  scope (new timeframe, new symbol), SCOPE.md gets edited and ENGINE.md
  silently keeps the old claim.
- **Fix:** Shrink ENGINE.md's section to the engine-only defaults
  (`--input-mode`, `--converter` flags) plus one line: "The research scope
  itself is defined in SCOPE.md." Delete the restated venue/instrument
  block.

### B5 — Dead metric fields: trainNetEv / testNetEv

- **Status:** ⏳ OPEN — awaiting user decision (schema change).

- **Severity:** low
- **Category:** simplify
- **Where:** `strategy-research-protocol/schemas/FAMILY.json.ts`
  (`OutcomeMetrics`), `strategy-research-protocol/MEMORY.md` (outcome
  fields table), `strategy-research-protocol/modules/Researcher.md`
  (metrics bullet: "stay null — no train/test split in gates v1"),
  `src/strategies/research/INDEX.json` (championMetrics carries the nulls).
- **Problem:** Two fields that are always null appear in four surfaces and
  every FAMILY.json, forcing each reader (and the Researcher on every
  outcome write) to re-learn that they mean nothing yet. They were reserved
  for a v2 train/test split that may or may not come.
- **Fix:** Either delete the two fields from the schema + docs + example
  (they can be re-added with a gatesVersion bump when a split actually
  exists — schema change, needs user approval), or leave as-is and accept
  the noise. Deletion is the simpler protocol; existing FAMILY.json files
  would need the two keys dropped (mechanical).
