# Protocol audit 2026-07-08--03

## Verdict

Healthy. This pass also verified the protocol's infrastructure promises for
the first time: every npm script the docs cite exists in package.json
(`backtest:research:btc:15m`, `research:check`, `research:check-batch`,
`research:build-index`, `research:protocol-size`) and both dashboard API
routes that judging depends on exist (`/api/backtests/[id]`,
`/api/batches/[batchUid]`). The five findings below are second-order:
the worst is an ambiguous stage-climb extension direction that would make
an agent guess flags at its very first gate-1 `go`. Runnable as-is.

## Findings

### C1 — Stage-climb extension direction is ambiguous, and the stage table duplicates tool invocations

- **Severity:** medium
- **Category:** confusing / duplication
- **Where:** `strategy-research-protocol/STAGE-GATES.md` (stages table,
  mechanism column: stage 2 `extendBacktest --latest --limit 2000`; stage 0
  `--sequential, batchUid --smoke suffix`; climb rules: "Extensions grow
  coverage backward contiguously (newest missing markets first)") vs
  `strategy-research-protocol/tools/extendBacktest.md` ("Default extension
  grows backward into older missing markets. `--latest` grows forward into
  newer missing markets.") and `tools/runBacktest.md` (smoke profile:
  `--latest --limit 10 --sequential`).
- **Problem:** Three-way muddle at the first gate-1 `go`: the climb rule
  says "backward … (newest missing first)" — self-contradictory on its
  face; the mechanism column says `--latest`, which extendBacktest.md
  defines as _forward_; the tool doc's _default_ is backward. An agent
  cannot tell whether stage 2 is "the 2000 markets immediately older than
  the covered window" (the intent) or "the 2000 newest missing". Separately,
  the mechanism column hardcodes tool flags whose semantics and home are
  the tool docs — a second home for invocations.
- **Fix:** In STAGE-GATES.md: (1) reword the climb bullet in plain terms —
  "stage 2 adds the 2000 markets immediately older than the already-covered
  window, so coverage stays one contiguous newest-first block"; (2) replace
  flag strings in the mechanism column with links ("extend per
  [`tools/extendBacktest.md`](./tools/extendBacktest.md)", "smoke per
  [`tools/runBacktest.md`](./tools/runBacktest.md)"). In extendBacktest.md
  state which invocation realizes the stage-2 intent, once.

### C2 — examples/ is validated by nothing and silently drifts

- **Severity:** medium-low
- **Category:** flaw / simplify
- **Where:** `strategy-research-protocol/examples/FAMILY.json`,
  `examples/FAMILY.md`, `examples/INDEX.json`;
  `strategy-research-protocol/scripts/research-check.ts` (validates only
  `src/strategies/research/`).
- **Problem:** The example files teach the format but no check validates
  them against the schemas — every schema change must remember to hand-edit
  them (the B5 field deletion required exactly that; forgetting would have
  shipped a wrong example that ProposeFamily might imitate). Meanwhile the
  repo now contains two REAL families that are always schema-valid and
  richer than the examples, and ProposeFamily.md already embeds a full
  FAMILY.json template inline.
- **Fix (preferred, smaller):** Delete `examples/` and repoint the two
  references (README layout row, protocol-improve reading list) at the real
  families under `src/strategies/research/` as living examples.
  Alternative (cost — new mechanism, needs approval): make research-check
  also validate the examples folder.

### C3 — ProposeFamily lacks the foreign-check-failure rule the Researcher got

- **Severity:** low
- **Category:** missing-link
- **Where:** `strategy-research-protocol/modules/ProposeFamily.md` (Final
  Self-Check: "Both files validate (`npm run research:check` passes for
  this family)") vs `strategy-research-protocol/scripts/research-check.ts`
  (all-families, exit 1 on ANY failure) vs the B1/A4 rule that lives only
  in `modules/Researcher.md`.
- **Problem:** A propose session running while a researcher session has
  another family mid-write can see `research:check` fail for reasons
  outside its new family — and its contract gives no rule, so it may stall
  or try to "fix" the other family.
- **Fix:** One sentence in ProposeFamily.md Final Self-Check: "check
  failures in OTHER families are not yours — if your new family validates,
  note the failure and finish."

### C4 — Operator reaction table is missing the dashboard-down stop

- **Severity:** low
- **Category:** missing-link
- **Where:** `strategy-research-protocol/OPERATOR.md` §2 reaction table
  (rows: working / polling / stopped validated-killed / stopped nothing
  actionable / crashed) vs `strategy-research-protocol/SESSIONS.md`
  preconditions and `tools/getBacktestResults.md` (session stops when the
  dashboard is down).
- **Problem:** The A2 fix introduced a new stop reason ("dashboard down —
  report and stop") that the operator's what-you-see table does not cover;
  the operator may misread it as "nothing actionable" and park the family.
- **Fix:** Add one row: `session stopped: "dashboard down"` → `npm run
dashboard`, then relaunch the same command.

### C5 — The bypassPermissions rationale is explained in four places

- **Severity:** low
- **Category:** duplication
- **Where:** `strategy-research-protocol/SESSIONS.md` ("Writing a new
  launch script" item 5 — the home), `strategy-research-protocol/OPERATOR.md`
  §2 permissions note, `scripts/researcher.sh` header,
  `scripts/propose-family.sh` header — each explains "headless denies
  non-allowlisted commands instead of asking".
- **Problem:** Same rationale defined four times; when the reasoning
  changes (e.g. a future allowlist), three copies go stale.
- **Fix:** Keep the full sentence only in SESSIONS.md item 5; OPERATOR and
  the two script headers shrink to "default bypassPermissions — rationale
  in SESSIONS.md".
