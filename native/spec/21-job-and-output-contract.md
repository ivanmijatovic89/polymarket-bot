# 21 — Job and output contract

This document defines the data that crosses the TypeScript/Rust boundary for
backtests: what a market job carries (including `ModelConfig`, the exchange
rules record, candidates and input integrity), what the engine returns, and
how TS turns that into the `RunSingleMarketOutput`/`MarketStats` it consumes
today. It also fixes the null-vs-zero-row and skip taxonomy, the closed
vocabularies and the number rules. These matter because one bad value aborts
the whole run's insert transaction. It defines the producer's ModelConfig
resolution and defaults, the execution metadata TS stamps around the binary,
and a single source of truth (JSON Schema generated from Rust) with validation
on both sides. Process mechanics (subcommands, exit codes, error classes,
streaming, the CLI flag matrix) are in
[20-binary-protocol.md](20-binary-protocol.md). Where a sub-object has
another owner (named in §6 and §7), the example here is a copy and the owner
wins.

## 1. Principles

| # | Principle |
|---|---|
| P1 | The rest of the app is unchanged. Aggregation, segments, batch stats, extend, the dashboard and research tools receive exactly the `RunSingleMarketOutput`/`MarketStats` shapes they get today (`src/backtest/runSingleMarket.ts:132-157`, `src/backtest/stats/marketStats.ts:16-61`). Additions are optional fields that TS stats ignore. |
| P2 | The job carries every input that changes a result. The binary never reads env, wall clock or network for behavior (requirement `job-carries-all-result-semantics`; D09). |
| P3 | The engine output is machine-independent. Machine identity and timing are stamped by TS around the binary call, never inside the deterministic result (requirement `execution-meta-stamped-by-ts`). |
| P4 | One schema source: Rust types, then JSON Schema, then TS types and validators (§3). No hand-mirrored types. Today `native.ts:160` does `JSON.parse(r.stdout) as TResult` with no validation. |
| P5 | Validate at every boundary. An invalid value fails one market (or one candidate), never the whole run's transaction (§19). |
| P6 | Built for speed. No replay when the result is known in advance (§13). The job is self-contained and local (no I/O decisions inside the engine) and small: no Gamma metadata and no raw rules JSON travel in it. Outputs are small and bounded (§16). |

### 1.1 Terms

| Term | Meaning |
|---|---|
| counted tick | A real (`book`, `price_change`) or synthetic tick that enters the tick pipeline, counted **before** the window gate (`produces_tick` and `on_synthetic` in 12 §5.2-§5.3). It increments `eventsProcessed` (§15), and the first one sets `marketId` (§11). TS: `dispatchTick` up to the gate (`runSingleMarket.ts:297-304`). |
| strategy tick | A counted tick that passes the window gate (12 §5.4) and calls the strategy (`dispatch` in 12 §5.2). Its 0-based index is the trace `seq` (22 §3.3). |
| effective ModelConfig | `run.modelConfig` with `execution` replaced by the candidate's `execution` when that is non-null (§8). Every `modelConfigSha256` is computed over an effective ModelConfig. |

## 2. Layers and data flow

```
producer (TS)  ── MarketJobData (BullMQ payload, TS-owned, §4) ──▶ worker shim (TS)
worker shim    ── resolves inputs to verified local files, builds EngineJob (§5) ──▶ binary
binary         ── EngineResult (§10): deterministic section + diagnostics ──▶ worker shim
worker shim    ── validates, stamps execution meta (§12), maps per candidate ──▶ RunSingleMarketOutput
aggregator     ── validates each MarketStats row against the DB contract (§19) ──▶ MySQL
```

- `MarketJobData` stays the BullMQ payload type (`src/backtest/jobTypes.ts:18-56`).
  It gains the native fields in §4. How a group's shared context is stored in
  Redis is decided in [40-fleet-integration.md](40-fleet-integration.md) and
  [41-candidate-groups.md](41-candidate-groups.md).
- `EngineJob` and `EngineResult` are Rust-owned. They contain only what the
  engine needs and returns. Fields such as `batchUid`, `commitSha`, `idx`,
  `order`, `timeDriven` and `marketMeta` never reach the binary.

## 3. Single source of truth

| Item | Rule |
|---|---|
| Source types | A Rust crate `pmb-contract` (no engine dependencies) defines `EngineJob` (including `ModelConfig` and the `market.rules` record), `EngineResult`, `LiveConfig`, the `serve` message unions (20 §6.2), the trace and ledger record types and the closed enums of §17, with `serde` (`deny_unknown_fields` on every struct) and `schemars` 1.x (JSON Schema 2020-12). |
| Schema files | `native/contract/schema/v<N>/*.schema.json` are generated by `cargo run -p pmb-contract --bin export-schema` and committed. `contractSha256` = sha256 over the bundle: files sorted by name, each in canonical JSON (§6.1), joined by `\n`. The binary embeds it ([20](20-binary-protocol.md) §3, §5.2). |
| TS types and validators | `npm run native:contract:gen` generates `src/native/contract/generated.ts` (json-schema-to-typescript) and standalone validators compiled with Ajv's 2020-12 class plus the custom keywords of §18. `npm run native:contract:check` regenerates both and fails on any diff. Hand-written TS types for these payloads are forbidden. `MarketJobData`, `RunSingleMarketOutput` and `MarketStats` stay TS-owned; their native sub-objects import the generated types. |
| Dependencies | `ajv` 8.x as a runtime dependency (the shim validates every result at runtime; the repo has only a transitive ajv 6, which cannot read 2020-12) and `json-schema-to-typescript` as a devDependency, both pinned to exact versions in M1 step 2 (01 §6). |
| TS tests | Contract and parity-tooling tests use `tsx --test` (node:test) through an npm script `native:test:ts`; `npm test` stays unconfigured (CLAUDE.md). |
| Closed objects | Every object in the contract is closed. There are exactly three opaque payloads, each validated by its own schema: `candidates[].params` (the strategy's `paramsSchema` from `describe`), `market.recorderV4.manifest` (the V4 manifest schema, 15 §5) and `intentMeta` entries (strategy-defined JSON, §16). The Gamma metadata passthrough (`GammaMarketMeta`, an open record) is not part of `EngineJob` (§5). |
| CI | (1) Re-export the schema and diff it (must be clean). (2) `native:contract:check` (clean). (3) `tsc`. (4) Golden fixtures under `native/contract/fixtures/` (jobs, results, one per skip and error case) deserialize and reserialize unchanged in Rust and validate in TS. (5) The TS engine's own `RunSingleMarketOutput` fixtures validate against the output schema. (6) `fixtures/model-config/{ts-compat,realistic}-default.json` with their `modelConfigSha256`: TS and Rust both reproduce the sha. (7) The seed vectors of 10 §6.1 RNG-7 pass in Rust and in `selftest` (20 §5.3). |
| Versioning | Any schema change bumps that schema's integer version ([20](20-binary-protocol.md) §3). TS keeps validators for every version it still accepts. |

## 5. `EngineJob` (binary input)

An `EngineJob` has two semantic sections, `run` (identical for every market of
a submission or group) and `market`, plus two non-semantic ones, `outputs`
and `budget`. In `serve` mode, `run` may be sent once as a `context` and
referenced by `runRef` ([20](20-binary-protocol.md) §6.2).

```jsonc
{
  "jobSchemaVersion": 1,
  "run": {
    "strategyId": "overnight-opus55-lagsnipe.v15.rs",
    "inputMode": "telonex-delta",                       // telonex-delta | recorder-v4 | journal
    "modelConfig": { "...": "§6" },
    "candidates": [ { "key": "<submissionUid>", "index": 0, "params": { }, "execution": null } ]
  },
  "market": {
    "slug": "btc-updown-15m-1780272000",
    "conditionId": "0x…",                                // null when unknown
    "window": { "startMs": 1780272000000, "endMs": 1780272900000 },  // see §5.2
    "tokenIds": { "UP": "…", "DOWN": "…" },
    "outcome": "UP",
    "rules": { "...": "§7 (shape owned by 11 §13.4)" },
    "gammaPriceToBeat": { "priceToBeat": 117234.51, "syncedAtMs": 1780280000000 },
    "feedAvailability": { "...": "owned by 14 §6.2" },
    "input": { "path": "/abs/…/btc-updown-15m-1780272000.parquet", "bytes": 1234567,
               "sha256": null, "format": { "name": "telonex-delta-typed", "version": 1 } },
    "recorderV4": null,                                  // { manifest, allowGaps } for recorder-v4 (15 §5)
    "ownActivity": null,                                 // calibration (15 I-39): { "ledger": {path, bytes, sha256},
                                                         //   "clock": {offsetMs, uncertaintyMs}, "maxPlacementMs", "restoreHorizonMs" }
    "feedFiles": [ { "feed": "binance_agg_trades", "symbol": "BTCUSDT", "day": "2026-06-01",
                     "path": "/abs/…", "bytes": 98765 } ]
  },
  "outputs": { "tracePath": null, "traceLevel": "decisions", "ledgerPath": null },
  "budget": { "wallMs": 120000, "threads": 1 }
}
```

`market.tokenIds` and `market.outcome` replace `MarketResolution`
(`src/backtest/stats/marketResolution.ts`): token ids per outcome are market
identity, and the outcome is used only for settlement. The shim
short-circuits a null resolution or outcome before the binary (§13).

### 5.1 Field rules

| Field | Rule | On violation (class: cause, 20 §4) |
|---|---|---|
| `run.strategyId` | equals the binary's strategy id (cf. `marketProcessor.ts:80-85`) | `invalid_input: strategy_id` |
| `run.inputMode` | in `capabilities.inputModes`. `recorded` and `telonex-paired` are rejected for native (20 §5.6). | `invalid_input: input_mode` |
| `run.modelConfig` | §6; `modelConfigVersion` in `capabilities.modelConfigVersions`; `rules.rulesTableVersion` in `capabilities.rulesTables` (11 VR3) | `invalid_input: model_config` / `rules_table_version` |
| `run.candidates` | 1..`maxCandidates` entries; §8 | `invalid_input: params` |
| `market.slug` | v1: `^btc-updown-(5m\|15m)-[0-9]{10}$` (D06). TS short-circuits a missing slug (§13). | `invalid_input: market` |
| `market.conditionId` | when present, MUST equal the market id seen on the first book event | `data_defect: foreign_file` |
| `market.window` | `startMs < endMs`, both safe integers, equal to the slug window (10 §5). `null` is allowed only for `recorder-v4` in `ts-compat`, which copies TS (`strategyWindow` is null for V4). `realistic` requires a window in every mode (D23). | `invalid_input: window` |
| `market.tokenIds` | distinct non-empty `UP` and `DOWN`; every asset in the input MUST be one of them (15 I-18) | `invalid_input: market` / `data_defect: foreign_file` |
| `market.outcome` | `UP` or `DOWN` | `invalid_input: market` |
| `market.rules` | §7 | `invalid_input: rules` |
| `market.gammaPriceToBeat` | Keeps today's tri-state: absent = not requested, `null` = catalog miss, object = resolved (`jobTypes.ts:47-48`). `priceToBeat` is a finite f64 or null. | `invalid_input: feed_availability` |
| `market.ownActivity` | null unless `features` contains `own_activity`; shape per 15 I-39 | `invalid_input: schema` |
| `market.input.path`, `feedFiles[].path`, the `ownActivity` path | absolute, local, existing. `r2://` and relative paths are rejected. | `invalid_input: path` / `data_missing: input_missing` (absent) |
| `market.input.bytes`, `sha256` | verified before replay when present (the shim verified them first, §9) | `data_defect: integrity_mismatch` (15 I-8) |
| `market.input.format` | `(name, version)` is supported by this binary. The reader refuses unknown versions (today `native/crates/pmb-replay/src/telonex.rs:73,441-443` hardcodes the converter layout). | `data_defect: format_version` |
| `market.feedFiles` | MUST cover every day the engine needs (window plus lookback, per feed). The engine checks coverage itself. | `data_missing: day_file_missing`, message names the fix command |
| `outputs.tracePath`, `ledgerPath` | `serve`: absolute and inside the executor's `--work-dir` (20 §6.1). `run`/`run-group`: any absolute path, from the job or the CLI flags that override it (20 §5.4). Written atomically. | `invalid_input: path` |
| `budget.wallMs` | 1,000..3,600,000 | `invalid_input: schema` |
| `budget.threads` | 1..256; the most pool threads this job may use (40 §7.2); never result-affecting (20 G5) | `invalid_input: schema` |

### 5.2 Window semantics

| Profile and input | Rule (owned by [12-engine-core.md](12-engine-core.md) §5.4) |
|---|---|
| `ts-compat`, `telonex-delta` | Strategy ticks whose decision timestamp is in `[startMs, endMs]`, **inclusive** (`runSingleMarket.ts:306-313`). |
| `ts-compat`, `recorder-v4` | `window` is null: no strategy gate; the V4 replay drops envelopes outside `[start, end)` on receipt time (15 §1). |
| `realistic`, every input mode | Strategy ticks while `now ∈ [startMs, endMs)`, half-open, on the receive clock (D23). At client time `endMs` the engine sends a cancel-market for this market with cause `WindowEnd`; orders it cancels end `Canceled(WindowEnd)`. `MarketClosed` is reserved for exchange-closed states: an order still resting at the exchange-side market close ends `Canceled(MarketClosed)`, and an order that arrives after the close is rejected `MarketClosed` (13 §6.6). |

### 5.3 No wall-clock rules inside the engine

TS today branches on `Date.now()` in two places: the 30 h fresh-market grace
for price-to-beat (`wireBacktestExternalFeeds.ts:121,314`) and the
today/yesterday logic for Chainlink day files
(`chainlinkCryptoPricesSource.ts:87-88`). The producer MUST resolve every such
decision into `feedAvailability` (status values defined in
[14-feeds-and-plugins.md](14-feeds-and-plugins.md) §6.2) and record `asOfMs`.
The binary MUST NOT read the wall clock for any result-affecting rule. This is
why `asOfMs` is not part of `ModelConfig`: an `--extend` resolves fresh
availability for its new markets, while the model stays equal to the parent's.

## 6. `ModelConfig` v1

`ModelConfig` is the complete, versioned set of model settings. The producer
resolves every field (§6.3): the binary applies no defaults, and a missing
field is `invalid_input`. It is stored on the run row (D09,
[42](42-persistence-and-stats.md)), inherited verbatim by `--extend`, and
echoed back by its hash. The version field is `modelConfigVersion`
everywhere (job, run row, echo).

### 6.1 Representation

These rules make the canonical form and hash unambiguous:

- Values are only strings, booleans, safe integers, objects and arrays. Money,
  sizes and ratios are decimal strings matching
  `^-?(0|[1-9][0-9]*)(\.[0-9]*[1-9])?$` with at most 6 fractional digits (no
  trailing zeros, no exponent). Other strings are printable ASCII without `"`
  or `\`, so no escaping can differ between serializers. Keys are ASCII. There
  are no floats.
- Canonical JSON = keys sorted bytewise at every level, array order kept, no
  whitespace. `modelConfigSha256` = sha256 of the canonical UTF-8 bytes. TS
  and Rust MUST compute the same hash (CI item 6, §3).
- Sub-object owners may add fields only with a `modelConfigVersion` bump.
- `ts-compat` parity runs MUST use zero jitter (`compatLatency.jitterMs = 0`),
  because TS jitter is unseeded and cannot be reproduced (requirement
  `seeded-rng-keyed-by-slug`).

### 6.2 Seed

The run seed, the per-market seed, the stream seeds, every draw and the value
mappings are owned by [10-domain-model.md](10-domain-model.md) §6.1 (RNG-1 to
RNG-7), with golden vectors. The contract consequences:

- `seed` is a JSON integer in `[0, 2⁵³ − 1]`, so it is exact in TS and fits
  the `seed bigint` column (42 §3.1). There are no u64 decimal strings (N2).
- The producer sets it from `--seed` (20 §5.6), else `0`. One seed per
  submission; a group and every `--extend` inherit it (D14).
- The binary echoes it (§10) and the shim asserts it (§12). It never chooses
  or changes a seed.

### 6.3 Producer resolution and defaults

The producer builds the ModelConfig of a fresh submission in this order, then
validates the result as a whole (13 §7.3 consistency, §6.1 representation)
and refuses an invalid one before enqueueing (exit 2). `--extend` skips all of
it and uses the parent row's `model_config` verbatim (42 §5).

- Calibration sets are committed JSON files under
  `native/contract/calibrations/latency/<id>.json` (content per 13 §7.4 and
  51 §13) and `native/contract/calibrations/feeds/<id>.json` (14 §9), read only
  by the producer and immutable once a persisted run used them. The resolved
  values (`execution.latency.components`, `clock.marketData.delay`, the
  `feeds` latencies) MUST equal the named set unless its id is `custom`; an override that changes them MUST also set that
  id to `custom` (exit 2 otherwise). 14 F-48 applies: changing a default
  publishes a new id. Exception: in `ts-compat`, `clock.marketData.delay` is
  always `{"kind":"constant","ms":0}` (12 §4.5) whatever its id says, and the

- Producer env knobs other than `BACKTEST_LATENCY_*` have no effect on native
  runs (20 §5.6 prints a warning). Worker env never matters (20 G2, G6).

## 7. `market.rules`

The per-market rules record is owned by
[11-exchange-rules.md](11-exchange-rules.md) §13.4: the producer sends only
the values it captured in snapshots (JC1), selected by
`src/db/exchangeRules.ts` per RS1-RS3, and the engine fills every absent field
from the compiled tables of `modelConfig.rules.rulesTableVersion`, classifies
the market (`RulesSource`, RS4) and validates the captured values (JC2). This
section fixes only the JSON types that the strict schema needs.

### 7.1 JSON types

```jsonc
"rules": {
  "snapshotParserVersion": 1,            // positive int; null iff "captured" is empty
  "captured": {                          // only captured fields; any subset of the keys below
    "tick": { "value": "0.01", "origin": "v4_bootstrap", "phase": "pre_start", "snapshotId": 812 }
  },
  "disagreements": 0                     // RS3 Gamma-vs-CLOB disagreements, int >= 0
}
```

Every `captured` entry is `{value, origin, phase, snapshotId}`:

| Key | Type |
|---|---|
| `origin` | `gamma` \| `clob` \| `v4_bootstrap` \| `live_gamma` \| `live_clob` (11 §13.1) |
| `phase` | `pre_start` \| `post_start` (`tick` only `pre_start`, 11 RS2) |
| `snapshotId` | positive safe integer (`exchange_rules_snapshots.id`) |

| Captured field (11 §13.4) | `value` type |
|---|---|
| `tick` | decimal string |
| `minSizeResting` | decimal string |
| `feesEnabled` | boolean |
| `feeType` | string, `^[a-z0-9_]{1,64}$` (an unknown type is accepted here and handled by 11 FE3) |
| `feeSchedule` | `{rate: decimal string, exponent: integer, takerOnly: boolean}` |
| `takerDelayEnabled` | boolean |
| `negRisk` | boolean |
| `version` | `v1` \| `v2` |
| `secondsDelay` | integer ≥ 0 |
| `minOrderAgeS` | integer ≥ 0 |
| `acceptingOrdersTimestampMs` | safe integer |

Any other key, a wrong type, a value 11 JC2 rejects (a tick outside 11 §7.1,
`exponent` outside FE3, a `version` outside V1), or `negRisk: true` (out of
scope, 11 V4; the producer refuses it first) is `invalid_input: rules`.

### 7.2 Profiles and milestones

- `realistic` builds its `RulesTimeline` from the record (11 X2) and outputs
  the rules provenance of §10. `ts-compat` validates the record, ignores the
  values (11 §4) and outputs `rules: null` (11 §13.8).
- Until the snapshot table exists (M3a, which also imports the files of the
  D37 capture, 11 §13.2), every job carries the empty form
  `{ "snapshotParserVersion": null, "captured": {}, "disagreements": 0 }`,
  which the engine classifies `fallback`.
- `tick_size_change` events override the tick in force (D21, 11 §7.5).
- Raw Gamma and CLOB JSON stay in the snapshot table and are never sent in a
  job (P6).

## 8. Candidates

```jsonc
{ "key": "<submissionUid of this candidate's run>", "index": 0,
  "params": { "...": "normalized by describe" },
  "execution": null }   // or a complete ModelConfig.execution object (13 §7.3)
```

| Rule | |
|---|---|
| C1 | Keys are unique. Indices are `0..N-1`, in array order. |
| C2 | Params are normalized (`describe`). Duplicate (params, effective `execution`) pairs are `invalid_input` (D14). |
| C3 | Every candidate's `requiredFeeds(params)` MUST be identical. Mixed feed requirements are rejected in v1 (D14). |
| C4 | Only `execution` may differ per candidate. `profile`, `seed`, `capital`, `clock` (12 §4.5: it shapes the shared input timeline), `feeds`, `runner`, `risk` and `rules` are shared. In the job, a non-null candidate `execution` is a **complete** object that replaces `run.modelConfig.execution` (the binary applies no defaults). The candidates file of [41](41-candidate-groups.md) §3.3 MAY express it as a partial override; the producer resolves that override against the run-level `execution` and puts the complete object in the job. Variant-safe keys are every key under `execution`, because `execution` holds only execution-model choices (13 §7.3); keys outside `execution` are never variant-safe. Each effective `execution` MUST be valid for the shared profile; `ts-compat` candidates cannot vary (pinned compat values, 13 §7.3). The profile never varies inside a group: cross-profile comparisons are separate runs (the profile pair of 13 §7.2). |
| C5 | Execution-model streams derive only from the market seed (`modelConfig.seed`, `market.slug`; 10 §6.1 RNG-2) and the stream tag (RNG-3); feed-latency streams are run-level, from `modelConfig.seed` and the feed tag (14 F-51). No stream depends on `idx`, candidate index, group composition or worker (requirement `seed-independent-of-idx`; D14). Each candidate gets its own stream instances, so a candidate's result equals its standalone run. |
| C6 | Isolation: no mutable state is shared between candidates ([20](20-binary-protocol.md) §5.5). |

Routing each candidate result to its run's aggregate, splitting duration
(D13; §12) and failure isolation across candidates are specified in
[41-candidate-groups.md](41-candidate-groups.md).

## 9. Input resolution (TS shim, before the binary)

1. Resolve `input.path` to a local absolute path. On a cache miss, download
   from `r2Url` into the canonical location (today `runSingleMarket.ts:386-415`).
   For `--read-from r2`, download to the job temp dir and delete it afterwards.
   The `[read-from] LOCAL hit / R2 download` log stays in TS.
2. Verify `bytes` (and `sha256` when known). A pre-existing local copy that
   fails: re-download once when the read mode allows it (40 §6.1), otherwise

3. Resolve `feedFiles` (window plus lookback) under the machine's data roots

   `data_missing: day_file_missing` before spawn, and the message names the

4. Short-circuit the cases in §13 without spawning.

```jsonc
{
  "outputSchemaVersion": 1,
  "status": "ok",                       // ok | error  (group-level)
  "error": null,                        // ErrorInfo when status = error
  "echo": { "engineVersion": "1.0.0", "engineCommit": "…", "strategyId": "…",
            "jobSchemaVersion": 1, "profile": "realistic", "seed": 0,
            "modelConfigSha256": "…", "rulesTableVersion": "rules-table-v1", "snapshotParserVersion": 1 },
  "market": { "slug": "…", "conditionId": "0x…", "rulesSource": "partial" },
  "candidates": [
    { "key": "…", "index": 0, "status": "ok", "modelConfigSha256": "…",
      "output": { "...": "EngineMarketOutput §11" } },
    { "key": "…", "index": 1, "status": "error", "modelConfigSha256": "…",
      "error": { "class": "strategy_fault", "cause": "panic", "message": "…",
                 "detail": { "callback": "onMarketTick", "seq": 1843, "tsMs": 1780272401234, "location": "src/bin/x.rs:88" } } }
  ],
  "resultDigest": "<sha256 of the serialized deterministic section>",
  "diagnostics": {
    "startedAtMs": 1791500000000, "finishedAtMs": 1791500000210, "wallMs": 210, "busyMs": 205, "cpuMs": 205,
    "peakRssBytes": 41000000, "thread": 3, "cache": { "hits": 2, "misses": 0 }, "skewMs": 9, "inputPath": "tape",
    "anomalies": { "staleBookEvents": 0, "inexact_decimal": 0, "skippedRows": { } },
    "counters": [ { "key": "…", "ordersPlaced": 4, "ordersRejected": { "post_only_would_cross": 1 },
                    "ordersCanceled": 2, "buyNotionalUsdc": "12.4", "sellNotionalUsdc": "0", "peakReservedUsdc": "6.2",
                    "strategyTicksSkipped": 0 } ]
  }

```

- **Deterministic section** = every field except `diagnostics`. Its
  serialization order is fixed by the Rust type, so `resultDigest` is
  comparable byte-for-byte across machines ([20](20-binary-protocol.md) G5).
- `echo.modelConfigSha256` is the run-level config's hash; each candidate's
  `modelConfigSha256` is the hash of its effective ModelConfig (§1.1).
  `echo.rulesTableVersion` is copied from `modelConfig.rules`;
  `echo.snapshotParserVersion` from `market.rules`.
- `market.conditionId` is the market id observed on the first counted tick
  (null when there was none). `market.rulesSource` is the RS4 classification
  (11 §13.3) computed by the engine, in both profiles; it is identical for
  every candidate of the market.
- `diagnostics` is never compared and never persisted directly; it holds
  metrics only (TS stamps its own times, §12). `skewMs` is the final
  exchange-time skew (12 §4.4 XT4). `inputPath` is `tape` or `v1` (16 §7.5
  NT-5). `anomalies` holds the data-anomaly counters of 15 §8 under the names
  used there (for example `staleBookEvents`, `inexact_decimal`, `skippedRows`
  by reason) plus the rules counters of 11 (`tick_inferred`,
  `fee_curve_differs_from_era`, …), the engine counters of 10 and 12
  (`duplicate_active_cid`, `reservation_dust`, `oversold_qty`, …) and the
  attribution counters of 13 §7.2; zero counters MAY be omitted. `strategyTicksSkipped` counts strategy
  callbacks skipped by the tick filter (16 TF-6); it is never part of
  `eventsProcessed`. `counters` cover
  the capital-aware counters (requirement `capital-aware-counters`); they are
  not persisted in v1, [42](42-persistence-and-stats.md) may add columns.
- `ErrorInfo = {class, cause, message, detail?}`. `class` comes from the
  closed vocabulary of [20](20-binary-protocol.md) §4, `cause` from 20 §4.1.
  `message` is one line of at most 1,000 characters. `detail` may carry
  `callback`, `seq`, `tsMs`, `location`, `path` and `fixCommand`.
- Live and paper windows emit the same `EngineResult` in `market_result`
  ([20](20-binary-protocol.md) §7).

## 12. Execution metadata stamped by TS

The binary never receives worker identity, and the deterministic result never
contains it. The shim builds `marketStats.execution`
(`marketStats.ts:16-25`) for every non-null `marketStats`. All times are taken
by the shim on the host clock; the binary's `diagnostics` are metrics only.
These are the rules of [40](40-fleet-integration.md) §7.1:

| Field | Value |
|---|---|
| `machineId` | `getMachineId()` of the host. varchar(32), indexed, drives the leaderboard. Today the native path leaves it NULL (`marketProcessor.ts:58` returns the binary JSON as-is). |
| `workerChildId` | `100 + slot`, the lowest free shim admission index at dispatch, so native slots never collide with TS child ids 1..N in displays |
| `startedAtMs` | shim wall clock at dispatch to the executor, after the token grant (process-per-job: spawn) |
| `finishedAtMs` | shim wall clock at result receipt (process-per-job: exit) |
| `durationMs` | single candidate: `finishedAtMs − startedAtMs`; group of `k` candidates admitted with weight `w`: `floor(w × (finishedAtMs − startedAtMs) / k)` per candidate (40 §7.1, 41 §7.4). Also the top-level `durationMs`. |
| `eventsProcessed`, `eventsByType` | copied from the engine output; for a group, each candidate gets the full count (D13) |
| `commitSha` | the shim's `WORKER_LAUNCH_SHA`, meaning "the TS shim code that ran the job". Engine identity (engine, version, commit, binary sha, profile, ModelConfig, seed) is stored per run (D09, [42](42-persistence-and-stats.md)). |

A job that succeeded in an isolated re-run (20 §6.3 S5) carries the stamps of
that run. `recorderV4Capture` is also stamped by TS from the manifest
(`runSingleMarket.ts:449-458`).

Before mapping, the shim MUST assert: `echo.profile`, `echo.seed`,
`echo.rulesTableVersion`, `echo.snapshotParserVersion` and
`echo.modelConfigSha256` equal the request; each candidate's
`modelConfigSha256` equals the hash the producer computed for its effective
ModelConfig; `echo.engineVersion` equals the value recorded at submission;
`market.slug` equals the job's slug; and the candidate keys and indices
exactly match the request, in order. A mismatch fails the job as
`invalid_output: echo_mismatch` (requirement `engine-provenance-persisted`).

## 13. Null-vs-zero-row and skip taxonomy

| Case | Who decides | `marketStats` | top-level `skipReason` | Persisted as | Counts in run denominators |
|---|---|---|---|---|---|
| activity (fills or open positions) | engine | full | absent | market row | yes |
| at least one counted tick, no fills, no UP/DOWN qty > 0 at the end (including when no tick passed the window gate) | engine | zero row, `skipReason: "no_in_window_activity"` | `no_activity` | market row (`runSingleMarket.ts:535-567`) | yes |
| no counted tick at all | engine | `null` | `no_activity` | failure row `no_market_stats: no_activity` (`aggregateProcessor.ts:36-49`), class `market_skip` | no |
| slug missing | TS shim, no spawn | `null` | `no_slug` | failure row, `market_skip` | no |
| `marketResolution` null | TS shim, no spawn | `null` | `no_resolution` | failure row, `market_skip` | no |
| outcome null | TS shim, no spawn | `null` | `unresolved_outcome` | failure row, `market_skip` | no |
| V4 coverage incomplete (gate owned by [15-inputs.md](15-inputs.md)) | V4 gate | `null` | `incomplete_capture` + `coverageReasons` | failure row, `market_skip` | no |
| candidate `strategy_fault` (panic, `cascade_limit`, `intent_meta_limit`) | engine | none: the candidate emits no `MarketStats` (12 §6.3, §11) | — | failure row for that candidate only (§14) | no |
| any other error class ([20](20-binary-protocol.md) §4) | engine or TS | — (job fails) | — | failure row with class-prefixed reason (§14) | no |

Rules:

- TS replays the full market today before returning `no_resolution` or
  `unresolved_outcome` (`runSingleMarket.ts:497-519`), and those outputs
  persist nothing but the reason. The shim MUST short-circuit them without a
  spawn, with `eventsProcessed: 0`. A job can never reach the binary in these
  cases, because `market.tokenIds` and `market.outcome` are required (§5.1).
  Parity tooling compares only `skipReason` for these markets.
- Zero-row money fields come from the same formulas (§11). They are non-zero
  only for split/merge-only activity. A difference there against TS is the
  TS merge-PnL bug and is classified, not copied.
- `coverageReasons`: 1..32 non-empty strings, each at most 512 characters.
- A new `marketStats.skipReason` value needs a DB migration and a TS mapping
  first (`src/db/schema.ts:200`).

## 14. Errors and failure rows

- Single-candidate job: an error class fails the BullMQ job, with the retry
  policy of [20](20-binary-protocol.md) §4.3. The reason stored in
  `backtest_run_failures.reason` is `<class>: <cause>: <message>` (20 §4.2).
- Group job: a group-level error fails the market for every candidate. A
  candidate-level `strategy_fault` fails only that candidate's run for that
  market ([41](41-candidate-groups.md) §7.3), except
  `strategy_fault: result_too_large`, which fails the job (41 §6.2).
- Deterministic classes (`invalid_input`, `data_defect`, `strategy_fault`,
  `engine_fault`, `invalid_output`, `killed`) MUST NOT burn retries
  (requirement `native-error-classification`).
- **`failure_class` and `failure_detail`** (42 §3.6): `failure_class` is the
  class (every class of 20 §4 except `canceled`) or one of the aggregator
  classes `market_skip` (every null-stats row of §13), `missing_child_result`
  (`aggregateProcessor.ts:138-147`) and `invalid_market_stats` (§19);
  `failure_detail` is the cause (20 §4.1). Both are validated in TS before
  insert. Legacy rows and TS-engine job failures keep both NULL.

## 15. `eventsProcessed` and `eventsByType`

- `eventsProcessed` = the number of counted ticks (§1.1), real and synthetic,
  counted before the window gate. This matches TS (`runSingleMarket.ts:297-300`)
  and is the same definition in both profiles, so leaderboard and simulator
  expectations stay comparable.
- `eventsByType` keys are the closed tick-cause vocabulary of
  [12-engine-core.md](12-engine-core.md) §5.3, identical in both profiles:
  `book`, `price_change`, `binance_agg_trade`, `chainlink_round` (the TS
  `event_type` strings). Trade prints never produce ticks in v1 (12 §5.2).
  Values are integers ≥ 0, and they sum to `eventsProcessed`.
- Implementation: a fixed array indexed by the cause enum, serialized once at
  the end. No map is touched on the hot path.
- Observed range (last 300k market rows, read-only DB sample, 2026-10-08):
  `events_processed` max 657,318. The key sets were
  {book, price_change, chainlink_round, binance_agg_trade} (99.9%),
  {book, price_change, binance_agg_trade}, and {book, price_change}.

## 16. `intentMeta` construction and caps

- Construction matches TS (`marketStats.ts:171-180`): walk fills in fill
  order. For each fill with meta, take the placing order's meta (each order
  of a `place_batch` has its own meta, `src/strategy/Strategy.ts:39,130`).
  Skip it if that client order id was already taken (first fill wins). Fills
  without a client order id are always included. Unfilled orders contribute
  nothing.
- Collection is lossless. TS harvests from a 500-entry `recentFills` ring
  (`src/trading/Portfolio.ts:140,838-841`), which can drop fills silently;
  that is classified as a TS bug. The engine keeps every fill of the market.
- Meta keys produced by plugins (`windowsMetrics`, `orderbookLevels`,
  `technicalIndicators`) keep their names, because research tools read
  `intentMeta[0]` and protocol tools parse `intent_meta` in SQL
  (`src/cli/research/export-trade-features.ts:230-236`). The SDK side is in
  [30-strategy-sdk.md](30-strategy-sdk.md).
- Key order inside a meta object is not significant (MySQL JSON normalizes
  it). Non-finite numbers in meta serialize as `null`, the same as
  `JSON.stringify`.
- Caps. Observed range (same sample): average 274 bytes per market, maximum
  1,982 bytes, maximum 10 entries.
  - Per order, serialized meta is at most 16 KiB. A larger meta makes the
    order fail validation with reject reason `meta_too_large` (deterministic,
    the same in live).
  - Per market, `intentMeta` is at most 1 MiB and 10,000 entries. Beyond
    that, the candidate fails with `strategy_fault: intent_meta_limit`.
    Results wait in Redis until aggregation and are inserted 250 rows per
    statement (`src/db/backtests.ts:136`).

## 18. Number rules

| Rule | Applies to |
|---|---|
| N1 | No NaN, Infinity or -0 anywhere. Fixed-point values cannot produce them. f64 values (feed prices, params) are checked finite at ingress. |
| N2 | No integer in any payload exceeds ±(2⁵³−1). The run seed is bounded for that reason (10 RNG-1); v1 has no u64 decimal strings. |
| N3 | Timestamps are integer milliseconds since the Unix epoch, UTC. |
| N4 | Job money, size, ratio and tick values are decimal strings (§6.1). Rust parses them from the text into 1e6 fixed point and never goes through f64. More than 6 fractional digits is `invalid_input`. |
| N5 | Output money and size values are JSON numbers rendered from fixed point at their quantization (2 dp or 4 dp): plain decimal digits, no exponent, no trailing-zero padding requirement. TS parses them to the nearest double, and `String(x)` in `toDecimal` (`src/db/backtests.ts:139-141`) reproduces the same digits, because values stay below 15 significant digits. |
| N6 | Ranges per column, as in the §11 table. Custom TS validator keywords: `decimalScale: k` (\|x·10ᵏ − round(x·10ᵏ)\| < 1e-6) and `columnRange`, because JSON Schema `multipleOf` is unreliable for binary floats. |
| N7 | Strategy params may contain f64 (they are strategy inputs). They are not part of `ModelConfig` and are compared as normalized JSON. |
