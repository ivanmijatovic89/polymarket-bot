# Committed fixture markets

Real markets committed with every input a native job needs, so CI runs
complete jobs without R2, MySQL or Redis (`native/spec/60-verification.md`
§12, FX-1 to FX-5). Generated by `scripts/native/fixtures-build.ts`; do not
edit by hand.

"Crossed or locked ticks" is the 15 §8 counter `crossedBookTicks`: ticks
after which at least one token's book is crossed or locked (best bid >= best
ask), counted with the TS telonex-delta reader
(`replayTelonexDeltaParquetForMarket`). `fixture.json` records it as
`anomalies.crossedBookTicks` and splits it into `strictlyCrossedTicks` (a
token with bid > ask) and `lockedTicks` (bid == ask, no token crossed);
those two names are not spec counters.

- **Three fee eras (FX-1):** F1 (`…1773969300`), F2 (`…1776556800`), F3
  (`…1787730300`). F0 (before 2026-01-05, no fees) is not required.
- **Chainlink coverage (FX-1, 14 F-19):** three 15m markets start after
  2026-04-02 (`…1776556800`, `…1777152600`, `…1787730300`), so lagsnipe
  and the feed exerciser have fixture runs.
- **Midnight start:** `…1776556800` starts at 00:00 UTC, so the 300 s
  lookback crosses midnight: two Binance and two Chainlink day files, and
  both seed rows come from the previous day (14 F-12, F-14, F-20, F-22).
- **Edge market:** `…1777152600` (F2): 587 crossed-or-locked book ticks
  (574 strictly crossed) and 8 backward steps of the Telonex local time
  (15 §8 `crossedBookTicks`, `localClockBackwards`). Found with
  `scan --max-bytes 600000`: every eligible local file up to 600 KB (F1 15m
  from the price-to-beat epoch, F2 and F3 15m inside Chainlink coverage, all
  BTC 5m) was replayed through the TS telonex-delta reader; local and
  exchange clock steps were counted in file row order with DuckDB. Among
  files with at least 1,000 in-window rows and both anomalies,
  `…1777152600` has the most crossed-or-locked ticks. No local file has the
  exchange clock going backwards: the converter sorts rows by exchange time
  (15 I-11). Crossed or locked ticks also occur in every other fixture.
- **BTC 5m (D38):** six local BTC 5m telonex files exist (2026-02-12, the
  launch day), so two are included: the two smallest with at least 1,000
  in-window rows; `…1770875700` also has a backward local-clock step. Both
  start before the BTC 5m price-to-beat epoch (2026-02-19T00:05Z), so the
  price-to-beat status is `absent_pre_series_epoch`, and before Chainlink
  coverage. The catalog has not verified their Binance feed
  (`binance_usable` is null; `fixture.json` records `"unverified"` under
  `catalogFeedChecks`); the proof below loads that feed through the TS
  loader, which fails loudly on missing or empty data.
- Small files were preferred among markets with rows across the window, a
  resolved outcome and no unusable feed (eligibility read through
  `src/db/telonexMarkets.ts` only).

## Layout

```
<slug>/
  job.json                         EngineJob (21 §5) of the engine exerciser, fixture-relative paths (FX-1a)
  fixture.json                     GF-2 header, provenance, bytes + sha256 of every file, price to beat, proof
  telonex-delta/<slug>.parquet     the converter output, copied byte for byte (canonical input)
  binance/aggTrades/BTCUSDT/BTCUSDT-aggTrades-<day>.parquet   trimmed day files (FX-2)
  chainlink/btcusd/btcusd-crypto-prices-<day>.parquet         trimmed day files (FX-2, covered markets)
```

The feed directories mirror the dataset roots (`BINANCE_DATA_BASE_DIR`,
`TELONEX_CRYPTO_PRICES_BASE_DIR`), so the TS loaders read the trimmed files
unchanged. The generator owns exactly these five entries per market:
`build` refuses to touch a market directory that holds anything else (FX-1
traces, snapshots or digests may go stale when the inputs change), and
`check` fails on any file `fixture.json` does not list.

### Jobs

`job.json` is the `EngineJob` for the Rust engine exerciser
(`engine-exerciser.rs`, params `{}`) with the committed ts-compat model
config (`native/contract/model-configs/ts-compat-default.json`). The
exerciser requests no feeds (60 §5.1, 30 §18), so the job is in the
producer's no-feeds form: no `gammaPriceToBeat`, `feedAvailability.priceToBeat`
null and no `feedFiles` (14 §6.2, 21 §5.1). The price to beat and every feed
day file stay in `fixture.json`.

`J=$(npm run -s native:fixture-job -- <slug>)` checks every file against
`fixture.json` (bytes and sha256), checks that `job.json` equals the job
rendered from `fixture.json`, and prints the path of the absolute-path job
(FX-1a; written under the OS temp dir). For another strategy, name it and
the feeds it requests:

```bash
npm run -s native:fixture-job -- <slug> --strategy-id overnight-opus55-lagsnipe.v15.rs --feeds all
npm run -s native:fixture-job -- <slug> --strategy-id <id> --feeds binance,price-to-beat --params '{"chainlink":false}'
```

`--feeds` takes `none`, `all` or a comma list of `binance`, `chainlink`,
`price-to-beat`; it is required with any `--strategy-id` other than the
exerciser and refused (other than `none`) for the exerciser. A requested
price-to-beat adds `gammaPriceToBeat` and `feedAvailability.priceToBeat`
(`fed` or `absent_pre_series_epoch`); each requested feed adds its day files
from `fixture.json`. A Chainlink request on a market before 2026-04-02 adds
no day file (the 14 F-20 day set is empty; the engine reports
`pre_coverage`, F-19).

Feed day files carry `bytes` but no `sha256` in the job: 14 §4.1 ("day files
carry no sha256") and 21 §5 (`FeedFile`) own the job shape and win over the
FX-2 sentence "the job records each trimmed file's byte size and sha256"
(00 §3.1). For fixtures, each day file's sha256 is in `fixture.json` and is
verified by `native:fixture-job` and by `check` before use.

Rendered jobs of all six markets in three forms (exerciser; lagsnipe id with
`--feeds all`; a feed-exerciser id with `--feeds binance,price-to-beat`)
deserialize, validate and round-trip unchanged through
`job_contract::EngineJob` (checked on 2026-10-09 with a scratch binary
outside the repository; a job-contract test is still to add, see "Open
points").

## Trimming (FX-2)

Per feed, one file per covered day (Binance: 14 F-12, the days covering
`[start - 300 s, end)`, end day excluded at midnight; Chainlink: F-20, from
`max(start - 300 s, 2026-04-02)`), written in the dataset schema with the
same columns, types and row order. Each file holds exactly:

- Binance: the trades with `start - 300000 <= ts_ms <= end + 2000` (F-13)
  plus the seed: the highest `agg_trade_id` with `ts_ms < start - 300000`
  in the covered day files (F-14), kept in the day file that holds it.
- Chainlink: the rows with round time
  `start - 300000 <= timestamp_us/1000 <= end + 5000` (F-21) plus the seed:
  the last row with an earlier round in `(server_timestamp_us, timestamp_us)`
  order (F-22).

Rows keep the source file order (`ORDER BY file_row_number`). The generator
refuses a seed tie. Binance files are written with ZSTD, Chainlink files
with Snappy, as the sources. The tails (2 s, 5 s) and the lookback (300 s)
are the engine constants of 14 §4.3.

Column names, column order, parquet physical types, repetition and DuckDB
types equal the source. Parquet annotations do not all match: the Binance
sources are DuckDB-written and match exactly, but the Chainlink sources come
from arrow-cpp (INT64 columns without a converted type, string columns with
the `StringType()` logical type), while the DuckDB-written copies carry
`INT_64` and no logical type. Every such difference is listed per file under
`trim.annotationDifferences` in `fixture.json`, so the fixtures exercise the
DuckDB annotation variant of the Chainlink schema, not the production one;
the production variant needs its own Rust reader test (see "Open points").

## FX-2 proof (interim)

`build` and `prove` run three checks per market; the fixture is installed
only when all pass.

1. **Trimmed rows** (`verifyTrimmedFeeds` in `scripts/native/fixtures-feeds.ts`),
   without reusing the trim predicates: every trimmed file is an
   order-preserving sub-multiset of its source day file; the TS loaders
   `loadBinanceAggTradesSeries` and `loadChainlinkCryptoPricesSeries` return
   identical series (`tsMs`, `visibleAtMs`, `value`, seed included) on the
   full and on the trimmed day files; and the trimmed files of a feed hold
   no more rows than that series. Together: exactly membership plus seed.
   The series digests are in `fixture.json` (`proof.feedSeries`).
2. **TS engine, full vs trimmed:** `runSingleMarket` (backtest mode,
   telonex-delta, no persistence) in a child process
   (`scripts/native/fixtures-oracle.ts`) with the OR-7 environment only
   (60 §2.3): `PATH`, `HOME`, `TZ=UTC`, the two data-root variables and every
   OR-7 knob from the committed ts-compat ModelConfig (feed latencies
   110/320/2700 ms, lookbacks 300 s, Chainlink max gap 300 s,
   `MAX_EVENTS_PER_DRAIN` 4200, `WEB_UI_ORDERBOOK_LEVELS` 10, and per D63
   `BACKTEST_LATENCY_DELAY`/`_JITTER` 0/0); `BOT_ENV` unset; starting
   capital and latency from the ModelConfig. The knobs are recorded in
   `proof.oracleKnobs`, and the generator fails when the OR-7 table
   (`scripts/native/oracle-env-audit.ts`) gains a knob it does not set. An
   observer hashes, per strategy tick (real and synthetic), the event type,
   exchange time, local time and the full `ctx.plugins.externalFeeds`
   snapshot, plus every decision and account event, and the per-market
   output without wall-clock fields.
3. **Pin:** the TS engine paths (60 OR-2) at HEAD equal the oracle pin and
   are clean (OR-3). `fixture.json` has the GF-2 header
   `{contentPin, generator, generatorSha256}` (D69 shape): `contentPin` is
   the oracle pin (OR-1, the `origin/main` commit last merged, today
   `ad2f11b8`) at which the content last changed; a rebuild at a later pin
   with identical content keeps it. `prove` reports a content mismatch
   (FX-3: regenerate, and cite the pin in the commit) separately from a pin
   that moved while the content stayed the same.

Strategy, until the TS feed-exerciser twin and trace writer v2 land (60
§5.8, 22 §3):

- Chainlink-covered markets: `feedsParityProbe.v1` (requests Binance,
  Chainlink and price to beat; no intents).
- Markets before 2026-04-02: every existing strategy that requests
  Chainlink hard-errors there by policy (14 F-19), so the oracle uses an
  inline probe `fixtures-feed-probe.binance-ptb` (Binance and price to beat;
  no intents).

Each runs with `tickOnUpdate` false and true. These probes have no intents
and no plugins, so DwellGate and TimeWindowGate on synthetic ticks (14
§12.4) and the canonical trace format are not covered yet; check 1 covers
the rows a probe trace never observes (lookback rows other than the last,
the seed, tail rows after the last tick).

`npm run native:fixtures:test` runs the committed tests on synthetic day
files: the trim selects exactly membership plus seed across a midnight
lookback, and `verifyTrimmedFeeds` fails when a lookback row, the seed or a
tail row is dropped or replaced, when an extra row is kept, when a column
the loaders do not read changes, when two rows swap, or when an 18-decimal
Chainlink price changes in a digit invisible as f64. It also covers the CLI
rules and the job shapes of every committed market.

## Commands

```bash
npm run native:fixtures:build -- scan [--max-bytes 600000] [--data-root DIR]  # read-only candidate and edge scan
npm run native:fixtures:build -- build [--slug a,b | --prune] [--data-root DIR]  # rebuild + prove (local data, MySQL read access)
npm run native:fixtures:build -- prove [--slug a,b] [--data-root DIR]         # re-run the proof; fails if it differs from fixture.json
npm run native:fixtures:build -- check                                         # offline: files, job.json, generator hash, 25 MiB cap
npm run native:fixtures:build -- jobs                                          # offline: rewrite job.json from fixture.json + model config
npm run native:fixtures:test                                                   # committed tests (synthetic data, no DB)
J=$(npm run -s native:fixture-job -- btc-updown-15m-1787730300)
```

`--data-root` defaults to `<repository root>/data` (01 §6 M1 step 1); the
feed roots are `<data-root>/binance` and `<data-root>/telonex/crypto_prices`,
and the Telonex file is the catalog's `data/…` path under it. `build` and
`prove` read the full day files there (read-only); `check`, `jobs`,
`native:fixtures:test` and `native:fixture-job` need only the repository.
`build` stages in `.staging/` (git-ignored) and replaces a market's
generated entries only after its proof passes. A full `build` refuses to
run while a committed market is no longer in the selection, unless
`--prune` is given. Every subcommand rejects positional arguments, flags it
does not take, repeated flags and malformed values (R14). `check` fails when
the generator files changed after the last build (`generatorSha256`), so a
generator change is committed together with its rebuild.

## Open points

- `D-PENDING` (generator): the exerciser id. 60 §5.1 says
  `engine-exerciser.rs`, the contract fixture `telonex-delta-ts-compat.json`
  uses `engine-exerciser.v2.rs`. The committed jobs use the spec id;
  `--strategy-id` overrides.
- `D-PENDING` (generator): `market.conditionId` should come from
  `telonex_markets.market_id` (15 I-18, 21 §4), which
  `src/db/telonexMarkets.ts` does not expose yet. The generator takes the
  file's constant `market` column (the same condition id), so nothing
  cross-checks the file against the catalog until that getter exists.
- The Rust Chainlink day-file reader needs a test on a production
  (arrow-written) day file, since the fixtures carry DuckDB annotations only.
- A job-contract test that renders every fixture job and round-trips it
  would make the check above part of `cargo test`, and `native:ci:local`
  should run `native:fixtures:build -- check` and `native:fixtures:test`.
