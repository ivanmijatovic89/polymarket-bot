# Committed fixture markets

Real markets committed with every input a native job needs, so CI runs
complete jobs without R2, MySQL or Redis (`native/spec/60-verification.md`
§12, FX-1 to FX-5). Generated by `scripts/native/fixtures-build.ts`; do not
edit by hand.

- **Three fee eras (FX-1):** F1 (`…1773969300`), F2 (`…1776556800`), F3
  (`…1787730300`). F0 (before 2026-01-05, no fees) is not required.
- **Chainlink coverage (FX-1, 14 F-19):** three 15m markets start after
  2026-04-02 (`…1776556800`, `…1777152600`, `…1787730300`), so lagsnipe
  and the feed exerciser have fixture runs.
- **Midnight start:** `…1776556800` starts at 00:00 UTC, so the 300 s
  lookback crosses midnight: two Binance and two Chainlink day files, and
  both seed rows come from the previous day (14 F-12, F-14, F-20, F-22).
- **Edge market:** `…1777152600` (F2): 574 crossed and 13 locked book ticks
  and 8 backward steps of the Telonex local time (15 §8 `crossedBookTicks`,
  `localClockBackwards`). Found with `scan --max-bytes 600000`: every
  eligible local file up to 600 KB (F1 15m from the price-to-beat epoch,
  F2 and F3 15m inside Chainlink coverage, all BTC 5m) was replayed through
  the TS telonex-delta reader (`replayTelonexDeltaParquetForMarket`),
  counting ticks where a token's best bid is above (crossed) or equal to
  (locked) its best ask; local and exchange clock steps were counted in
  file row order with DuckDB. Among files with at least 1,000 in-window rows
  and both anomalies, `…1777152600` has the most crossed ticks (the next
  are 349 in F2 and 91 in F3). No local file has the exchange clock going
  backwards: the converter sorts rows by exchange time (15 I-11). Crossed
  and locked ticks also occur in every other fixture.
- **BTC 5m (D38):** six local BTC 5m telonex files exist (2026-02-12, the
  launch day), so two are included: the two smallest with at least 1,000
  in-window rows; `…1770875700` also has a backward local-clock step. Both
  start before the BTC 5m price-to-beat epoch (2026-02-19T00:05Z), so
  `feedAvailability` is `absent_pre_series_epoch`, and before Chainlink
  coverage. The catalog has not verified their Binance feed
  (`binance_usable` is null; `fixture.json` records `"unverified"` under
  `catalogFeedChecks`); the proof below loads that feed through the TS
  loader, which fails loudly on missing or empty data.
- Small files were preferred among markets with rows across the window, a
  resolved outcome and no unusable feed (eligibility read through
  `src/db/telonexMarkets.ts` only).

## Layout

```
<slug>/
  job.json                         EngineJob (21 §5), fixture-relative paths (FX-1a)
  fixture.json                     provenance, bytes + sha256 of every file, price to beat, proof
  telonex-delta/<slug>.parquet     the converter output, copied byte for byte (canonical input)
  binance/aggTrades/BTCUSDT/BTCUSDT-aggTrades-<day>.parquet   trimmed day files (FX-2)
  chainlink/btcusd/btcusd-crypto-prices-<day>.parquet         trimmed day files (FX-2, covered markets)
```

The feed directories mirror the dataset roots (`BINANCE_DATA_BASE_DIR`,
`TELONEX_CRYPTO_PRICES_BASE_DIR`), so the TS loaders read the trimmed files
unchanged.

`job.json` is the `EngineJob` for the Rust engine exerciser with the
committed ts-compat model config
(`native/contract/model-configs/ts-compat-default.json`). Its market section
is complete: input with bytes and sha256, every feed day file with bytes,
`gammaPriceToBeat` and `feedAvailability`. `npm run -s native:fixture-job --
<slug>` checks every file against `fixture.json` and prints the path of the
absolute-path job (FX-1a; written under the OS temp dir). Options:
`--strategy-id <id>`, `--params '<json>'`, `--feeds none` (for a strategy
that requests no feeds: no price to beat, no feed files) and `--out <file>`.
Rendered jobs (both forms, all six markets) deserialize, validate and
round-trip unchanged through `pmb_contract::EngineJob` (checked locally with
a scratch binary on 2026-10-09; see "Open points").

## Trimming (FX-2)

Per feed, one file per covered day (Binance: 14 F-12, the days covering
`[start - 300 s, end)`, end day excluded at midnight; Chainlink: F-20, from
`max(start - 300 s, 2026-04-02)`), written in the dataset schema with the
same columns, types and row order. Each file holds exactly:

- Binance: the trades with `start - 300000 <= ts_ms <= end + 2000` (F-13)
  plus the seed: the highest `agg_trade_id` with `ts_ms < start - 300000`
  in the covered day files (F-14), kept in the day file that holds it.
- Chainlink: the rows with round time `start - 300000 <= timestamp_us/1000
<= end + 5000` (F-21) plus the seed: the last row with an earlier round
  in `(server_timestamp_us, timestamp_us)` order (F-22).

Rows keep the source file order (`ORDER BY file_row_number`). The generator
refuses a seed tie, checks the written row count and checks that column
names, DuckDB types and parquet physical types equal the source. Binance
files are written with ZSTD, Chainlink files with Snappy, as the sources.
The Chainlink sources come from arrow-cpp and the trimmed copies from DuckDB
1.5.2, so footers and converted-type annotations differ while the logical
and physical column types match. Every file's bytes and sha256, and the
source's path, bytes, sha256 and row count, are in `fixture.json`.

The tails (2 s, 5 s) and the lookback (300 s) are the engine constants of
14 §4.3.

## FX-2 proof (interim)

`build` runs the TS engine twice per variant, once with the full day files
under `data/` and once with the trimmed files, and only moves the fixture
into place when both traces and both outputs are byte-identical:
`runSingleMarket` (backtest mode, telonex-delta, no persistence, latency
0/0, feed latencies 110/320/2700 ms and Chainlink max gap 300 s pinned to
the model config) with an observer that hashes, per strategy tick (real and
synthetic), the event type, exchange time, local time and the full
`ctx.plugins.externalFeeds` snapshot, plus every decision and account
event, and the per-market output without wall-clock fields.

Strategy, until the TS feed-exerciser twin and trace v2 land (60 §5.8, 22
§3; branch `ws/ts`):

- Chainlink-covered markets: `feedsParityProbe.v1` (requests Binance,
  Chainlink and price to beat; no intents).
- Markets before 2026-04-02: every existing strategy that requests
  Chainlink hard-errors there by policy (14 F-19), so the generator uses an
  inline probe `fixtures-feed-probe.binance-ptb` (Binance and price to beat;
  no intents).

Each runs with `tickOnUpdate` false and true. The `true` variant gives the
strategy a tick on every Binance trade and Chainlink round, so a missing or
extra row inside the membership range changes the trace. A local negative
check confirmed it: dropping one in-window row from a trimmed Binance file or
from a trimmed Chainlink file (with `fixture.json` patched to match) failed
the `tickOnUpdate=true` proof, while `tickOnUpdate=false` alone did not
detect it (that row was never the visible value at a real tick).

## Commands

```bash
npm run native:fixtures:build -- scan [--max-bytes 600000]  # read-only candidate and edge scan
npm run native:fixtures:build -- build [--slug a,b]         # rebuild + prove (needs local data and MySQL read access)
npm run native:fixtures:build -- prove [--slug a,b]         # re-run the proof; fails if it differs from fixture.json
npm run native:fixtures:build -- check                      # bytes/sha256 of committed files and the 25 MiB cap
J=$(npm run -s native:fixture-job -- btc-updown-15m-1787730300)
```

`build` and `prove` read the full day files under `data/` (read-only);
`check` and `native:fixture-job` need only this directory. `build` stages in
`.staging/` (git-ignored) and replaces a fixture only after its proof passes.

## Open points (`D-PENDING` in the generator)

- `feedFiles[]` in the contract (21 §5, `FeedFile`) has no `sha256`, while
  FX-2 says the job records each trimmed file's bytes and sha256. The job
  carries bytes; every sha256 is in `fixture.json`, and `native:fixture-job`
  verifies all of them before rendering. `market.input.sha256` is set.
- The exerciser id: 60 §5.1 says `engine-exerciser.rs`, the contract
  fixture `telonex-delta-ts-compat.json` uses `engine-exerciser.v2.rs`. The
  committed jobs use the spec id; `--strategy-id` overrides.
- `market.conditionId` should come from `telonex_markets.market_id` (15
  I-18), which `src/db/telonexMarkets.ts` does not expose; the generator
  takes the file's constant `market` column (the same condition id).
- The committed job keeps the price to beat and feed files although the
  engine exerciser requests no feeds; the spec defines an error only for the
  opposite case (14 §6.2). `--feeds none` renders the strictly minimal job.
- A pmb-contract test that validates every rendered fixture job would make
  the round-trip check above part of `cargo test`.
